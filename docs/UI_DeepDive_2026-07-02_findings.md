=== SUBSYSTEM SUMMARIES (not yet seen) ===

## list-panels
The five list panels share one architecture — a DispatcherTimer polls a RynthAi C-export returning ANSI JSON, and hand-built Avalonia control trees (StackPanel-of-rows, no virtualization anywhere except LogPanel's accidentally-defeated ListBox) render it — but they span three generations of update strategy: NavPanel rebuilds its entire tree every 1s tick with no change gate at all (worst; also resets waypoint scroll every second); MonstersPanel/ItemsPanel rebuild-on-change but with holes (MonstersPanel full-rebuilds whenever captured combat stats tick, ItemsPanel wholesale-replaces its state object every poll causing silent edit loss); MonsterDamagePanel is the house-best pattern (JSON string gate, widget cache, in-place cell updates, editing-focus gate) and only needs its cache-prune and marshal-cadence tightened. The dominant runtime cost in the daily config is rebuild-churn interacting with the compositor: any panel that rebuilds at 1 Hz fires LayoutUpdated, which sets FloatingPanelHost._dirty and defeats the 2026-06-29 dirty gate (confirmed present in-tree at AvaloniaOverlay.cs:3873/4086 with the radar/RynthAi alwaysRender exemption at 2140 — status: known-fix-in-source), forcing per-second RTT+CopyPixels+UpdateLayeredWindow on undocked panels and overlay-texture invalidation docked. Beyond perf, two functional bugs stand out: MonstersPanel's five TextBoxes lack the AvaloniaTextInputActive wiring every other panel has, so docked text entry (rename/priority/expression/add-monster) is broken by the focus-yank + key-forwarding gate in Win32Backend/AvaloniaOverlay; and LogPanel's count-based Clear goes permanently blank once the 256-line ring is full. Ranking by need of the MetaPanel treatment: NavPanel (1), MonstersPanel (2), LogPanel (3), ItemsPanel (4), MonsterDamagePanel (5 — already treated, minor follow-ups).

## rynthai-dataflow
The RynthAi plugin->engine UI transport is pull-based: the engine-side Avalonia RynthAiPanel (RynthCore/src/RynthCore.Engine/UI/Panels/RynthAiPanel.cs) polls the plugin C export RynthPluginGetSnapshotJson every 33ms on the Avalonia UI thread; the plugin (RynthSuite .../LegacyUi/LegacyDashboardRenderer.cs BuildSnapshotJson) hand-serializes a JSON blob on the caller's thread into a per-thread HGlobal ANSI buffer, so the bot/pump thread is never blocked by publishing (data is pushed into volatile fields/ref-swapped arrays from OnTick, read lock-free or copy-under-lock by the serializer). Panel update strategy is healthy — fully in-place with equality-guarded setters, no Rebuild-per-click (unlike MetaPanel) — and StatusPanel/OverlayHost are trivial and clean; the LegacyUi ImGui renderer is dormant in the daily config (EnableImGuiShell=false) and survives only as the data/command broker. The prior dirty-gate fix #1 IS in the working tree (FloatingPanelHost._dirty + HeartbeatMs=200 + alwaysRender exemption for radar+RynthAi popouts, AvaloniaOverlay.cs:3855-4090, 2140) — known-fix-in-source — while roadmap fix #3 (OnInput blocking Dispatcher.UIThread.Invoke at AvaloniaOverlay.cs:3967) is still unfixed for the overlay agent's scope. The dominant costs found: (1) the 33ms poll rebuilds/marshals/parses a fat 10-30KB snapshot (equipment appraisals, 60 chat lines) with zero change-gating even though the panel discards 80% of it — the single biggest lever is splitting lean vitals (readable engine-locally from PlayerVitalsHooks with no JSON at all) from the fat 1Hz status payload plus a version-gate; (2) GradientBrush allocates fresh brushes per segment per tick, keeping the docked full-canvas overlay re-rendering at 30Hz permanently (segment 0 invalidates even with no target); (3) UI-thread exports mutate live bot state (profile/nav/subsystem/patrol) directly, racing the pump thread — the meta-command ConcurrentQueue pattern already in the file is the proven fix; and (4) click paths do full settings JSON serialization + two disk writes synchronously on the UI thread. Cross-thread reads themselves are largely safe (engine vitals/name/pose brokers are lock-guarded caches or [ThreadStatic] scratch buffers; profile lists copy-under-lock), so the remaining hazards are the write-side command paths, not the snapshot reads.

## radar-vision
Of the four panels, RadarPanel is the only true custom-render surface and dominates the cost picture: a 33 ms DispatcherTimer polls the plugin's JSON export, fully re-marshals (PtrToStringAnsi) and re-deserializes the snapshot 30x/s, then unconditionally InvalidateVisual()s — even when the fetch failed or nothing moved — which keeps the whole docked overlay compositing at 30 Hz; undocked, the host-level alwaysRender exemption (confirmed present in source at AvaloniaOverlay.cs:2140/4086, i.e. the 2026-06-29 fix #1 IS in the working tree) makes the radar popout RTT-render + CopyPixels + UpdateLayeredWindow at the full 16 ms tick unconditionally. Inside RadarSurface.Render, ~10 FormattedText, 2 Typefaces, ~8-12 pens/brushes, 3 Dictionaries and (in rotate mode) a StreamGeometry per fill strip are allocated per frame, and every wall segment is CPU-projected and drawn as an individual DrawLine with an O(walls x strips) visited test — all of it affine, so it is cacheable behind a PushTransform. Data-driven dirty is viable without violating the alwaysRender invariant: the panel knows exactly when the snapshot changed (raw-JSON compare or a plugin change-counter), heading/marker motion naturally marks dirty every poll while moving, and the 200 ms heartbeat covers the rest. Tracker and Nav are cheap, well-behaved pollers — Nav is exemplary with ordinal change-detection before touching controls — but Vision pushes the full settings JSON to the plugin (which persists to disk) plus writes 2+ synchronous log lines per slider drag sample, and Radar/Tracker both do a synchronous settings-file write per slider sample/wheel notch on the UI thread. No eager-Avalonia-static dispatcher-poison risk found in these four (all brushes are plain Color/IBrush statics inside panel classes constructed at panel-create time); no off-thread AC access; plugin-delegate caching is safe because old plugin modules are intentionally leaked, never freed.

## chat-settings
This slice (chat panel, chat filters editor, settings panel, panel-state store) is structurally healthy: chat ingestion is incremental (100ms poll, source-generated JSON, per-rule regexes compiled once at edit/load time, append-not-rebuild per line, 500-line cap), PanelStateStore writes are already debounced to drag-end via LayeredWindow's WM_EXITSIZEMOVE latch (so no per-pixel file I/O), and the 2026-06-30 lazy-brush dispatcher-poison fix is confirmed in RynthChatPanel with a strong guard comment in EntryPoint.cs:728-742. The dominant costs are full control-tree rebuild triggers, not steady-state: the chat search box and the filters editor rebuild the entire ≤500-line scrollback per keystroke (the filters editor also does a synchronous settings-file write per keystroke), each rebuilt line allocating a fresh FontFamily+SolidColorBrush. The worst defect is SettingsPanel's 5s poll: its Dirty edit-guard is dead code (never set true), so the visible tab is torn down and rebuilt every 5 seconds unconditionally — clobbering in-progress text edits, closing the keyboard gate mid-typing, and doubling as the accidental mechanism by which conditionally-visible rows appear (so any fix must pair the poll gate with explicit rebuild-on-structural-toggle). Two panels (RynthChatFiltersPanel, SettingsPanel) still carry eager Avalonia brush statics — currently safe because only Create() touches their statics on the UI thread, but they are exactly the latent invariant-4 recurrence class. Selection/clipboard is cheap (O(500) highlight walks, Win32 clipboard with a ≤50ms retry sleep on release only); the SimpleTheme spinner-glyph artifact is fixed in these files via DisableInnerScroll/per-box scrollbar disabling. All findings apply to both docked and undocked paths since these panels render in either.

## input-routing
Input flows two ways. DOCKED: AC's subclassed WndProc (Win32Backend.WndProcHook) hit-tests against lock-protected rect snapshots published by RefreshHitTestSnapshot (rebuilt on every layout pass and every capture, so staleness is <=1 frame) and forwards via non-blocking PostMessage to the off-screen Avalonia HWND — the game thread never waits, and click-to-pixel is roughly PostMessage + dispatcher slice + 16ms capture tick + next EndScene present (~20-50ms, healthy). UNDOCKED: each LayeredWindow WndProc runs on AC's game thread and its OnInput hop is still a blocking Dispatcher.UIThread.Invoke (roadmap fix #3 NOT done), so every mouse move over a popped-out panel stalls the game thread for a full UI-thread round-trip that includes four sequential visual-subtree walks and several synchronous open-write-close log-file appends per click. Worse, the blocking game->UI Invoke edges form a deadlock cycle with the UI->game RunOnGameThread SendMessage used by FloatingPanelHost creation/Show/LayeredWindow.Dispose — a plausible source of intermittent whole-client freezes. The 2026-06-29 dirty-gate fix #1 IS in source (per-host _dirty, 200ms heartbeat, alwaysRender exemption for radar/RynthAi, input/size dirtying) but is substantially defeated in live botting sessions because Avalonia's LayoutUpdated fires globally per layout pass of the shared root, so any docked panel churn re-dirties every floating panel. The single worst NEW find is config-specific to the daily driver: with EnableImGuiBackend=false the WndProc still enqueues every mouse/key/focus message into Win32Backend._pendingInput, which is only drained by ImGui's NewFrame — unbounded queue growth for the entire session on 32-bit VA. The undock-input-poisoning fix (stale PointerCapturingHost) is present and sound; Ctrl-gated radar click-through is correct apart from a minor wheel-routing latch wart. Keyboard routing relies on hand-wired per-TextBox AvaloniaTextInputActive toggles and the wiring is missing entirely in MetaPanel and MonstersPanel; the undocked pointer dispatch table lacks wheel-scroll, ComboBox, and ListBox handling. Cheapest wins in order: gate/cap the ImGui input queue, convert OnInput (and the redock/close callbacks) to Post while keeping OnMoved/OnResized synchronous per invariant, make LayeredWindow.Dispose post its DestroyWindow instead of SendMessage-blocking, and scope the floating dirty-gate's LayoutUpdated handler to actual subtree bounds changes.

## launcher-app
The launcher (RynthCore.App.Avalonia) is a single ~3,500-line code-behind MainWindow plus an always-on MemoryTabView, with no MVVM layer — everything (process probing, file I/O, Win32 window pings, UI mutation) runs on the Avalonia UI thread. Overall health is decent: settings writes are atomic with .bak recovery, Process handles are disposed per tick (the 2026-06-03 leak fix is in source), engine.json writes are corruption-guarded, and the auto-relaunch/reaper logic is carefully scoped. The dominant cost is the 2 s session tick: a full system process snapshot, per-client Process.Modules enumeration + SendMessageTimeout window pings, 2 directory sweeps, and per-PID JSON reads — all synchronous on the UI thread and scaling linearly with client count, so the launcher stutters worst exactly when many clients are running or one is hung. Second is the per-account character-detection path that re-reads (and for uncached accounts, re-scans the whole ThwargLauncher directory) every 2 s and unconditionally replaces every character-dropdown ItemsSource, which also disrupts an open dropdown. The Memory tab starts two more timers at XAML load (a second 2 s process scan + 5 s sampling) whether or not the tab is ever opened, and the sparkline rebuilds its full geometry with per-render allocations on every mouse move. All findings are new (the prior deep-dive context covered engine/panel code, not the launcher); none violate the hard invariants, and fixes are mostly small: background the probe phase, cache monotonic per-PID facts, and diff-before-rebind list updates.

## dcomp-assessment
The Dcomp folder is a Phase-A/B test harness, not a shippable overlay: a bar window (DcompOverlayWindow) plus free-floating DcompFloatingPanel windows that host the SAME shared panel Create() trees as production, positioned over AC via a 60Hz polling AcWindowTracker and owner Z-order (GWL_HWNDPARENT), gated at EntryPoint.cs:687 which SKIPS AvaloniaOverlay.Start entirely (no docked composite exists in this mode). The critical strategic fact is recorded in the source itself (DcompOverlayBootstrap.cs:149-169): true GPU DirectComposition modes (WinUIComposition/LowLatencyDxgiSwapChain) were tried and contend with AC's D3D9 Present on DWM's vsync budget, dropping AC to ~8fps whenever the overlay is dirty — so the harness is pinned to RedirectionSurface + Software rendering on the UI thread. That means the path does NOT deliver GPU rendering; its genuine win is structural: damage-driven OS-window presentation replaces the GDI path's manual per-tick RTT+CopyPixels+UpdateLayeredWindow, and each panel is an independent per-client HWND (good multibox story). However, with the 2026-06-29 dirty gate now confirmed in the GDI FloatingPanelHost (AvaloniaOverlay.cs:4085-4089, 200ms heartbeat), the remaining perf delta is presentation-only and modest, and the alwaysRender radar/RynthAi popouts (AvaloniaOverlay.cs:2140) re-raster per frame under either path. Meanwhile the Dcomp harness is missing keyboard input (WS_EX_NOACTIVATE everywhere), persistence, Chat/ChatFilters/Damage panels, docked mode (Phase C explicitly deferred), and is hot-reload-fatal (no teardown anywhere, yet its bar has a live RL button). Verdict: NOT worth investing in now as a perf play — finish the GDI roadmap fixes instead; keep Dcomp as a future UX/windowing migration (multibox cascaded visibility, real OS windows) whose ship-it precondition list is the findings below, roughly 1-2 weeks of work plus a focus/fps-governor unknown that could sink it.

## avalonia-hygiene
The Avalonia UI stack is in materially better shape than the 2026-06-29 dive: the undocked dirty-gate (fix #1) IS in the working tree (per-host _dirty + LayoutUpdated hooks + 200ms heartbeat + alwaysRender exemption, AvaloniaOverlay.cs:3857-4092), the LFH-corruption class is systematically hardened (grow-only chunked RTT/DIB/pixel buffers everywhere on the hot paths), all panel DispatcherTimers stop with the visual tree, and the dispatcher-poison fix (lazy RynthChatPanel brushes + EntryPoint guard comment) is in source. The dominant remaining steady-state cost in the daily config is the RynthAiPanel 33ms poll loop: it rebuilds, marshals, and JSON-parses the FULL dashboard snapshot (equipment appraisals + 60 chat lines + 4 profile lists) every tick, and its segmented target-HP bar assigns a freshly-allocated SolidColorBrush per segment per tick — which perpetually invalidates the visual tree, so the docked custom-Skia producer re-rasterizes and ReadPixels the entire game-client-sized surface at ~30 Hz even when the bot is idle. The MetaPanel roadmap fixes #2/#3/#4/#6 are confirmed NOT implemented (collapse/expand still full-rebuild ~420 controls, action buttons still fire-and-forget with up-to-2s dead click, undocked OnInput still a blocking Invoke off AC's game thread); #5 is half-done (LastFiredMs excluded from PayloadSig but CurrentState/CurrentMetaPath still in it, so botting still triggers autonomous rebuild flashes). One new threading finding: the blocking game-thread→UI-thread Invokes in FloatingPanelHost combined with UI-thread→game-thread SendMessage in RunOnGameThread form a real AB-BA deadlock window during multi-panel popout/restore. Remaining findings are lower-grade hygiene: 141 eager brush statics across 12 panel classes (latent invariant-4 recurrences), a per-frame allocation pile in RadarPanel.Render, an idle-work LogPanel timer, a leaked RTT on the software-fallback capture path, and unvirtualized 500-1000-child chat/meta StackPanels.
